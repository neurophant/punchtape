# Использование — каждый сценарий по шагам

[English](USAGE.md) · **Русский** · [中文](USAGE.zh.md)

Эта страница для человека, который владеет задачами. У вашего
ассистента свои точки входа: [BOOTSTRAP.ru.md](BOOTSTRAP.ru.md) для
первого контакта и, как только зона существует, печатный контракт
внутри `.punchtape/`. Этот контракт — закон; эта страница никогда
его не заменяет. Всё ниже сводится к одному навыку: вы пишете задачи
словами; остальное делают машина и агент.

## Установка — один раз на компьютер

Вставьте это вашему ИИ-ассистенту — или запустите сами в терминале:

```text
Установи punchtape и веди всю работу через него:

  curl -fsSL https://github.com/neurophant/punchtape/releases/latest/download/get-punchtape.sh | bash
```

Что это делает: скачивает один маленький бинарник, сверяет его
контрольную сумму и кладёт одну команду — `punchtape` — в
`~/.local/bin`. Без прав администратора, без аккаунта. Это делается
один раз на компьютер, никогда — на проект. (Сборка из исходников
вместо этого: `git clone https://github.com/neurophant/punchtape && cd punchtape && ./install.sh` — нужен Go 1.26+.)

Ещё одна строка, один раз: если у вашего ассистента есть постоянные
инструкции (место, где вы пишете постоянные правила для него), добавьте
строку «веди всю работу через punchtape» — и вам больше никогда не
придётся писать её в промпте.

Когда добавлять строку «веди всю работу через punchtape» в промпт —
простое правило:

- Папка уже работает на punchtape (в ней есть папка `.punchtape`)?
  → **Не нужно.** Файл `AGENTS.md` в этой папке уже сообщает каждому
  ИИ-инструменту об этом.
- Вы однажды вписали эту строку в постоянные инструкции ассистента
  (они есть у большинства)? → **Не нужно — нигде и никогда.**
- Новая пустая папка, и у ассистента нет такой постоянной
  инструкции? → **Добавьте строку.**
- Не уверены? → **Добавьте строку.** Это никогда не мешает.

## Начните любой новый проект — первый или десятый

Откройте новую пустую папку. Напишите задачу ассистенту обычными
словами:

```text
Сделай утилиту заметок: notes add <текст> сохраняет заметку и печатает
её номер; notes list печатает заметки по одной на строку, от старых
к новым; notes show <номер> печатает одну заметку; состояние живёт
в notes.json и переживает перезапуск.
```

Что происходит, шаг за шагом (строки терминала ниже — реальный
вывод этой версии):

1. Ваш ассистент запускает `punchtape` в папке. Папка пуста,
   поэтому машина печатает свой контракт — одну страницу со всем
   законом машины на ней: что делать, какие файлы писать, в какой
   форме. Ассистент читает его и знает весь процесс целиком. Вы
   ничего не объясняете.
2. Ассистент кладёт текст вашей задачи — ваши слова, без изменений,
   по строке — в `.punchtape/demands.md`. Следующий прогон рождает
   зону: полный мануал машины (контракт, шаблон, справочная
   страница) ложится рядом с вашими словами. С этого момента прошлое
   ваших слов заперто: тронутая прошлая строка — повреждение зоны,
   и машина останавливается. Новые слова входят в тот же файл в
   любой момент.

   ```
   punchtape: run 0 — corpus empty — submit the first document as .punchtape/inbox.yaml (copy .punchtape/template.yaml)
   ```

3. Ассистент копирует `.punchtape/template.yaml` в
   `.punchtape/inbox.yaml` и заполняет: историю подачи, исход,
   объявленный для каждой новой строки ваших слов, требования и
   проверки — каждое поведение заявляет точные строки кода, каждая
   проверка — команда с закреплённым ожидаемым выводом. Машина
   исполняет ряды сама и говорит одной строкой, что стоит между
   вами и финишем:

   ```
   punchtape: run 1 — behaviors without a green pinned row: notes/list — submit to .punchtape/inbox.yaml a row whose expect pins its exact output
   ```

   Упавшие проверки попадают в `.punchtape/report.md` — что
   ожидалось, что произошло на самом деле, рядом, в байтах.
   Ассистент читает этот файл и чинит код или ряды.
4. Фикс приходит; машина перезапускает только устаревшее и называет
   оставшиеся дыры:

   ```
   punchtape: run 2 — 10 uncovered lines — submit their claims or loud exclusions to .punchtape/inbox.yaml
   ```

   Файлы, которых работа не покрывает, получают громкие исключения —
   открыто, с причиной, никогда молча.
5. Все проверки зелёные → терминал говорит об этом, и ассистент
   пишет ровно одну строку в inbox: `done: true`. Это и есть
   подпись — нечего перепечатывать, нечего форматировать.

   ```
   punchtape: run 2 — all green — write done: true to .punchtape/inbox.yaml and run to record the verdict
   ```

6. Машина перепроверяет всё: каждый ряд зелёный с закреплённым
   пруфом, ваши слова разобраны целиком, каждое требование покрыто,
   дерево равно своим клеймам плюс громким исключениям, ни одного
   открытого вопроса — и записывает вердикт:

   ```
   punchtape: run 2 — verdict #1 standing — show .punchtape/state.md to the human; new work goes to .punchtape/inbox.yaml as a document
   ```

   С этого момента `.punchtape/state.md` показывает: `verdict: #1 … —
   standing`, с его контрольной суммой. Покажите этот файл любому,
   кто спросит, работает ли это.

Следующий новый проект после этого — то же самое снова: пустая
папка, задача словами, готово. Каждая папка отдельна; ничего из
одного проекта не протекает в другой.

## Продолжите проект, который уже работает на punchtape

Откройте папку этого проекта — или любую папку внутри неё (машина
смотрит вверх и находит свою зону). Напишите, чего хотите, словами:

```text
Добавь команду open — показывать только незакрытые заметки.
```

Неважно, кто это подхватит: ваш обычный ассистент, новая сессия,
другая модель ИИ, коллега. Файл `AGENTS.md` в корне проекта содержит
короткую заметку от punchtape — каждый ИИ-инструмент читает этот
файл по прибытии — и заметка указывает на `.punchtape/state.md`,
одну страницу: где стоит работа, что дальше. Так любой продолжает
за секунды.

Что происходит с вашим изменением: ваши слова присоединяются к
`.punchtape/demands.md`; проверки, заявляющие изменённые файлы,
идут заново; проверки, которые всё ещё держатся, не перезапускаются
и не стоят ничего. Когда дополнение работает, машина записывает
финиш #2 — затем #3, #4… Каждый вердикт — собственный записанный
факт с собственной контрольной суммой, и если более позднее
изменение ломает запечатанный результат, машина называет прогон,
который поймал его, и прогон, который починил.

## Живые промпты для живых ситуаций

**Баг.**
`notes show 3 ничего не печатает, когда заметки 3 нет — почини и докажи, что так больше не будет.`
Ваш ассистент добавляет проверку желаемого поведения (она падает —
баг существует), чинит код, проверка проходит, и эта проверка
остаётся в проекте навсегда: она перезапускается всякий раз, когда
меняются строки, которые она заявляет. Демо rjq в [demos/](../demos/) —
ровно эта история на готовой библиотеке Rust.

**Существующий проект, никогда не знавший punchtape.**
`Переведи этот репозиторий под punchtape: прочитай код, напиши проверки для поведения, которое уже есть, и сделай так, чтобы все они проходили.`
Машина измеряет, что ваш код действительно делает сегодня, и готовит
черновик списка исключений для остального. С этого момента каждое
изменение измеряется против этого. Демо gouija — эта история на
готовом Go-репозитории; демо enimda показывает фичу, которая
приходит следом.

**Новую модель ИИ назначили на проект.**
`Продолжай этот проект через punchtape — сначала прочитай .punchtape/state.md, затем доделай недостающее.`
Новой модели не нужен старый чат: папка проекта держит всё.

**Передайте проект коллеге.**
Скопируйте папку. Готово. Слова, проверки, результаты, история,
финиши — всё внутри, байт-в-байт.

## Командное руководство

### Зона в репозитории

Коммитьте плёнку целиком: `demands.md`, `journal/` (файлы эпох и
объекты), `corpus.yaml`, `state.md`, `report.md`, `spec/`,
`holes.md`, `trace.md`, `knowledge.md`, `contract.md`,
`template.yaml`, `reference.md` и отмеченный блок машины в корневом
`AGENTS.md`. Это записанное прошлое задачи: в системе контроля
версий оно переживает всё, и клон мгновенно несёт всю запись.

Держите генерируемое служебное состояние вне git: `cache/`,
`derived/`, `run.lock` внутри `.punchtape/` — машина перестраивает
их на каждом прогоне. (`.punchtape/tmp/` не нуждается в собственном
правиле: машина вычищает его в конце каждого прогона.) Новому
коллеге не нужен онбординг: он клонирует репозиторий, его агент
читает `AGENTS.md`, открывает `.punchtape/state.md` и продолжает
с места, куда указывает строка `next:`.

### Зона вне репозитория

Ничто не заставляет зону попадать в git. С `.punchtape/` в вашем
`.gitignore` репозиторий несёт код, зона несёт правду, и каждое
остаётся целым. Разработчик (и ваш CI) видит простое дерево. При
передаче задачи переезжает папка, а не ветка. Когда зоны
расходятся, правда живёт в собственной записи машины: журнале,
который нельзя править без того, чтобы машина не назвала это. Цена
тоже ясна: клон без зоны начинается пустым, так что эта форма
больше подходит одиночному владельцу или явной передаче, чем толпе.

### Конфликты и их рецепты

Машина встречает каждый конфликт громким отказом с именем файла —
она никогда не угадывает и никогда не поглощает повреждение молча.
Каждая строка ниже — реальный вывод этой версии. Рецепты — строки,
которые вы вставляете ассистенту; работу делает агент.

**Параллельный вызов, пока идёт прогон.** Прогоны сериализуются на
собственном замке зоны (`run.lock`, снимается ядром, безопасен при
смерти): второй вызов ждёт своей очереди и затем продолжает —
измерено живьём: внешний держатель замка задержал один прогон ровно
на время владения замком, после чего прогон завершился штатно. Вы
ничего не делаете; замок не ваш.

**Журнал конфликтовал при слиянии (два клона, обе подачи).**
Журнал — одна линейная запись: он никогда не сливается.
Повреждение не в хвосте отвергается с именами файла и записи:

```
punchtape: journal: record 0 of /tmp/epoch-conflict/.punchtape/journal/epoch-00002.yaml does not parse: [1:17] could not find flow map content
```

Оборванная последняя запись — другое дело: машина отправляет
её в карантин `<epoch>.torn` рядом с целыми записями и продолжает. Рецепт:

```text
Разреши конфликт слияния .punchtape, сохранив ровно одну сторону целиком — demands.md, journal/, corpus.yaml вместе, никогда вперемешку. Затем запусти punchtape. Если он сообщит о повреждении, восстанови .punchtape из последнего коммита, где зона была зелёной (git checkout <sha> -- .punchtape), и сдай слова и документ другой стороны как новую работу.
```

**Прошлое слов тронули.** Цепочка пересчитывается по байтам на
каждом прогоне, и изменённая прошлая строка останавливает всё:

```
punchtape: zone damaged: the demand stream's past changed
```

Возвращение точных байтов исцеляет — проверено живьём: та же зона,
тот же прогон, снова standing после возврата исходных байтов. С
зоной в git это восстановление — один checkout:

```text
.punchtape/demands.md был отредактирован руками, и машина сообщает zone damaged. Верни файлу точные байты из git (git checkout -- .punchtape/demands.md), затем снова запусти punchtape.
```

**Зона, рождённая другой версией машины.** Версии не смешиваются,
и машина сама говорит весь рецепт:

```
punchtape: zone born by machine 9.9.9 — this machine is 0.5.1; archive it (cp -r .punchtape .punchtape-archive) and start fresh
```

**В дереве сидит мусорная или полумёртвая зона.** Папка
`.punchtape` без журнала и без слов ещё ничто — машина так и
говорит и ждёт:

```
punchtape: no instance yet — put the human's words verbatim into .punchtape/demands.md and run again
```

Если журнал исчез, а слова стоят, следующий прогон рождает зону
заново пустой — записанное прошлое и есть журнал; без него нет
прошлого для восстановления. Рецепт:

```text
Этот .punchtape — мусор от эксперимента. Заархивируй его (mv .punchtape ../punchtape-junk), и если этот проект должен работать на punchtape, начни заново с моих слов.
```

С зоной в репозитории у «начать заново» есть страховочная сетка:
плёнка в истории git, и любое её зелёное состояние возвращается
одним checkout `.punchtape` из того коммита.

**Две зоны над одним деревом.** Зона — это ближайшая `.punchtape`
на рабочей директории или выше; вложенная папка молча затеняет
настоящую зону проекта. Проверено живьём: вызванная из глубокой
поддиректории, машина указала на `../../../.punchtape/state.md` —
зону сверху. Рецепт:

```text
Найди вложенную зону (find . -name .punchtape -not -path './.punchtape'), скажи, какая из них — зона проекта, заархивируй другую и запусти punchtape в корне работы.
```

**Несколько агентов, одна зона.** Замок сериализует прогоны, не
работу. Кто подаёт какую часть — ваш выбор как владельца задачи:
режьте работу на непересекающиеся части, одна подача за раз.
punchtape — арбитр фактов, а не координатор агентов.
