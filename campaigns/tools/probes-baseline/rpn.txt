# Working with punchtape

punchtape owns the state (.punchtape/, survives restarts) and
computes readiness. Three verbs:

- next — the one current slot (situation, action, example, gates);
  a fresh session starts with `next --full`.
- submit <file|-> — submit the slot's YAML delta; an accepted submit
  answers with the next slot after "NEXT SLOT:" — keep going
  without calling next; a rejection is one line — fix and submit
  again. Submit until the reply prints a VERDICT line; show it to
  the human and stop. Uncertain about the form — submit --check
  <file|-> runs the same validation with NO state change (a
  rejection costs nothing; a schema error caught here never
  reached the loop).
- why <topic|ID> — price, stage, latency, coverage, spec (the spec
  registry of this instance; `spec <words>` searches features,
  scenarios and expected texts — all words must meet), or an entity
  BY ITS ID: `why REQ-<n>`, `why SCN-<n>` (a kind word before the
  id — requirement, scenario, decision… — is stripped and changes
  nothing; `why` is the verb, there is no `card` verb).

Exit codes (the stop contract): 0 ok; 1 rejected; 2 failure; 3 choice
required — an open question batch rides the reply: relay it verbatim
to the human or proceed (silence applies the recommended defaults);
4 escalation — an open conflict question needs an explicit human
choice, silence does not resolve it; the loop holds until the answer.

## The check table (the spec you write)

    kind: checks
    submission-key: checks-001
    rows:
      - seeds:              # state files before the run
          - notes.json []
        materials:          # project files copied into the run
          - sample.bin      # byte-for-byte, same path (binary inputs)
        run:                # one command per element, two forms:
          - notes add A     # a string "cmd args" (spaces split,
          - [notes, add, B] # quotes group) or an argv list (no
                            # splitting: commas/quotes ride as-is);
          - notes list      # arbitrary argv — surface entries, tools,
                            # shell; all but last exit 0 (build state);
                            # the last is asserted
        out: "1 A"          # exact stdout of the last command;
                            # "(contains) X" — substring, not bytes
                            # (unpredictable bytes around the pinned
                            # fragment: harness timings, random ids)
        rc: 0               # its exit code (0 when omitted)
        state:              # "<path> <json>" structural; "<path> text
          - notes.json {...} # <bytes>" exact; "<path> absent"; escapes
                            # \n \t \r \\ \xNN in seeds and bytes
        volatile: [stdout]  # bytes the wish itself declares
                            # unpredictable (random ids, timestamps):
                            # stream names or state-file paths — the
                            # machine checks behavior, not those bytes

Same seeds+materials+run replaces that row — submit in parts, resubmit.
An optional `key:` on a row is its stable repair identity: while the
row has never gone green, a resubmission with the same key replaces
it even with different seeds and run (a broken row's repair must not
orphan the broken original — keep the key while you iterate); once
the row is proven green, the key's changes go through the
change-request hold like any other.
A real submission enters the canon and moves the stage — to try a
form first, run `submit --try <file>` with a ONE-row checks delta:
the same runner in a clean dir (twice, determinism checked), the
answer is the outcome; nothing is recorded, the stage does not move.
Build state by calling the tool; every command family needs a row
(uncovered ones are named); boundary rows welcome. A gap the human
accepts rides "kind: waive" (rule, target, reason): the rule stops
blocking, the verdict keeps showing it with the reason.

Expectation values (out/err/stdin/assertion values) take \xNN byte
escapes only: a literal backslash is \x5C, and lone \n, \t or any
loose backslash is rejected at input — write real control characters
(YAML double quotes or a block scalar decode them).

The YAML subset (what decodes reliably): plain mappings and lists;
in a flow list [a, b] the comma separates ELEMENTS (for run — whole
commands): `run: [tool, src, out]` is THREE one-word commands, not
one command with two arguments — one command with arguments is ONE
element (`tool src out` or the argv form [tool, src, out]); an
argument containing a comma goes as a quoted string or in the argv
form;
in a flow MAP {k: v, ...} the comma separates ENTRIES: a value with
a comma or ": " inside goes in double quotes —
`{id: a, scope: "one line, per note"}` — a torn value is repaired
once by the machine, quoting is the reliable form; seeds are the
ROW's own list (under seeds:), never elements of run — a run
element is one command, a seed under run is not a seed;
block scalars (|, >) for long texts — the only home of multiline
values; double/single quotes for values with `,` or `:` in them.
Outside the subset (not promised to decode): anchors (&/*) —
inline the values; block scalars
inside flow maps ({... |}) — quote the text or use block form; a
real newline inside a one-line quoted scalar breaks it — long
texts go as block scalars. A bare null/~ decodes to nothing —
quote it when the literal word is the value.

Every normal check runs twice in clean run directories and the two
runs must match byte-for-byte: full streams AND the full file set
of the run dir (not only the seeded files). Bytes the wish itself
declares unpredictable ride "volatile"; a build tool writing its
working directory into the run dir belongs outside it (the surface
decides), or declared volatile.
Run-dir determinism recipes (ephemeral bytes — random identifiers,
timestamps): normalize inside the row when the bytes carry no
meaning; declare the file volatile (on the row, before its first
run) when the wish itself says the exact bytes are unpredictable.
Declaring volatile on a row whose check has already run (after code
started) is an assertion like any expectation change: the machine
holds it for a human (kind: amend).

## Commands, seeds, materials — the machine is agnostic

The machine knows nothing about your product or environment: it
runs commands and reads bytes. Every run line is plain argv;
command[0] resolves in this order:
1. a file already in the run directory (seed, material, or the
   output of an earlier command of this row);
2. a surface entry: with a recipe (kind: conventions) the declared
   artifact — regular files only, symlinks are not transferred —
   materialized at its declared path, and command[0] spells the
   entry by that path (`bin/tool`, not `tool`; `out: "."` puts
   the project files at the run-dir root; files OUTSIDE the
   artifact do not reach the run dir — put runnable inputs inside
   the artifact); without a recipe, a project file at the
   command[0] path (the file you submitted) is the entry directly;
3. otherwise the name goes to the environment as-is (PATH: sh,
   sleep — anything your environment provides).
Inside a shell (`sh -c ...`) the run directory is the working
directory but not on PATH — call run-dir files as `./name`; the
right to execute is the file's own (copies of surface entries are
made executable; seeds and outputs keep what they got).
Each command runs in its own process group; whatever it leaves
running is killed when the row ends, before observations.

Long-running helpers, waits, orchestration: yours, in the row
itself —
    run:
      - sh -c 'helper ... & helper2 ... & sleep 0.3; caller ...; kill %1 %2'
Every command of the row runs under its own timeout; the machine
observes only stdout/stderr/exit-code/files.

A check-table row declares its own ceiling with `timeout-sec: <n>`
when its shape needs more than the delivery default (10 s,
limits.yaml check.timeout-default-s) — long-running helpers must
still finish and exit inside the row.

Seeds are plain one-line strings `<path> <content>` (one file per
line) — escapes \n \t \r \\ \xNN decode in seed and text-bytes
contents, in check-table seed lines AND in scenario seed maps
({path: …, content: …}) alike — one decoder, one rule: BYTE LITERALS
GO IN SINGLE-QUOTED YAML ('\x00\x01\xFF…'); double quotes decode \xNN
into unicode runes at the YAML level and the bytes are wrong before
the machine sees them. A seed already in the canon may ride by
reference instead of bytes: check-table line `<path> @<digest>` or
scenario map {path: …, digest: …} — the machine substitutes the
bytes (digests come from the FILES WRITTEN block / prior
transactions); resolved bytes give the same row identity as the
full text, so later rows reference the same seed without
retransmitting it. update-scenario replaces exactly the fields you
name; unnamed fields stay — clear an unwanted `pre` with `pre: []`. materials are project-root-relative file
paths (`materials/sample.bin`, not `sample.bin`), copied into the run
byte-for-byte under the same path (binary inputs never travel
through your hands).

## Assertions and the surface call

Observation vocabulary (assertion full form):

- stdout | stderr: conditions contains, equals, absent (the stream
  is empty), json-equals, json-contains.
- exit-code: conditions equals, fails (a non-zero exit; no value).
- file (path required): conditions exists, not-exists, contains,
  equals, absent (the file does not exist), json-equals,
  json-contains, bytes-equals.

EOL tolerance, one rule: text comparisons on FILES (file contains,
file equals) normalize CRLF→LF on both sides before comparing
(cross-OS stability); EVERYTHING ELSE is byte-strict — streams
(stdout/stderr), and file bytes-equals (the compact
`state: <path> text <bytes>` compiles to it). Pick the channel
knowing its semantics: a CRLF-vs-LF divergence is green through
file equals, red through bytes-equals and through any stream pin.

Byte literals go in SINGLE-quoted YAML — this includes
expectations (out:, err:, the state text tail, assertion values)
and seeds: a double-quoted "\xE4" is decoded by the YAML layer
into UTF-8 text (two bytes), not the one byte you meant, and the
machine refuses it at intake; single-quoted '\xE4' reaches the
value's own literal layer and pins exactly one raw byte.

Compact assertion lines in scenarios: out:, err:, rc:, fails:,
state-is: <file> <json> (= file json-equals).

The action (`when`): a quoted command string `"<name> <args...>"`
(surface cli, timeout 10 s) or the full mapping — surface: cli;
command: [<argv>]; stdin: <text or null>; timeout-sec: <n>; volatile:
[stream names or state-file paths]. Scenario setup lives BESIDE
`when`, at the scenario level: seed (files with content), materials
(project files, one `{from: <path>}` per entry) and pre (argv
commands, each must exit 0); check-table rows have no pre — their
setup is the earlier run commands.

operations (kind: spec, add-scenario/update-scenario: seed,
materials, pre) — never anywhere under run (a run element is one
command, a seed under run is not a seed). On deliver, checks deltas that REPLACE the
expectations of rows that have proven green are change requests

(proven greens are untouched; the cycle reopens and the new rows
run with the same submission) — a mixed delta partitions by row:
free rows apply, the replaced rows wait as the deferred part; the
spec channel is the same: additions and repairs of rows that never
proved anything are free, changes to proven rows or to requirement
boundaries are change requests. An open deferred edit resolves only
through kind: amend (approve | reject); while it is open, other
substantive submissions are REFUSED with the edit's key and the
resolve path (combine your rows into one delta and submit it after
the decision) — conflict findings (kind: lint, dimension:
conflict) are accepted at any moment. After exit code 3 read the

Answers to question batches ride your checks delta as "answers:"
[{question: Q1, option: b}]. A batch closed by silence (defaults)
still accepts a late explicit answer: the recorded default is
upgraded to your explicit choice (an already explicit choice stands
— the reply names it, nothing is dropped silently). An amend
approve of a held change does NOT close the sibling question batch:
only caller submissions spend the silence budget, machine-internal
replays do not speak for the human. A malformed delta is answered
with the canonical skeleton of its kind — fix by the skeleton and
resubmit.

caller counter for this submission; the machine books it as the
call's price. No trailer and `# TOKENS n/a` are equivalent and

submission-key is optional: an omitted key is derived from the

## Delivering code

The machine runs your product only through the check rows: the runner
materializes the surface into a clean run dir — whatever the operator
declared as the build artifact (kind: conventions, plain commands,
`out` names the artifact: a file or a whole tree) or, without a
recipe, the files you submit at the command[0] paths — and runs the
row argv as-is (surface entries resolve inside the run dir, anything
else goes to PATH). Teach the recipe once or submit the runnable
surface files with your code; optional types/lint commands ride the
same delta; without them the static gates are not applied.

The machine checks ARE the test suite: write no private suite, do
not re-run the whole suite — write code, the gates report the red.

After the verdict: a changed wish = new rows (or a spec delta) in
this same instance; a new task = a new instance.

Changing the expectations of a row that has proven green (after code
started) is not yours to apply: the machine holds such a submission
as an open amendment and a human asserts it (kind: amend) — silence
keeps the proven expectations. Adding new rows stays free. Rows that
prove nothing repair freely — the machine re-runs and re-probes the
replacement on the next run (a weak replacement stays red): a row
reported by the coverage-probe gate as green on a broken surface,
and a row that has never been green.

Never edit inside .punchtape or write project files by hand —
everything goes through submit. The knowledge renders live INSIDE
the instance data (.punchtape): specs/ — the human spec, one file
per feature (index.md is the registry; what the product does, in
living words) plus SPEC.md, SUMMARY.md and CHANGELOG.md; all
machine-written and regenerated on every verdict — read them, do
not edit. The working root keeps exactly one machine file: this
AGENTS.md. The instance has two zones with
different write rules: the curated zone (.punchtape/passport/) —
product knowledge the machine accumulates and shows through
`why passport` / `why diary`; and the hidden service zone — state,
the mutation journal, the ledger, locks and cache/snapshots under
.punchtape/cache/ (rebuilt from the journal, safe to delete). Every
data file carries a machine header naming its writer verbs; hand
edits are detected and refused.
